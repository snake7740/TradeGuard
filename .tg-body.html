TradeGuard · 方案展示02
01 · WHY

交易欺诈已从「单笔攻击」演变为「团伙化、工业化」

单交易视角的决策引擎，越来越难以应对组织化欺诈的关联性

痛点一：团伙化、工业化欺诈

测卡攻击（Card Testing）、账户盗用（ATO）、跑分洗钱，往往由同一团伙、同一设备、同一收款方在多个账户间协同完成——孤立地看每一笔交易，难以识别跨账户的关联。

痛点二：多源信号分散

交易流水、征信、舆情、投诉分布在各自独立的系统里，风控人员需要手工汇总，既慢又容易遗漏，错过处置的黄金窗口。

痛点三：告警疲劳与处置断链

低风险告警数量庞大导致疲劳；高风险处置又缺乏统一的审批与审计闭环，处置动作是否合规、能否追溯，缺少体系化保障。

价值主张

以 多 Agent 协同替代「人工告警流水线」：低风险事件自动处置、高风险事件证据化调查、全部处置动作合规可追溯——把风控人员从重复劳动中解放出来，聚焦真正需要判断的高风险案件。

监管背景：《银行卡业务管理办法》、反电信网络诈骗法规、金融监管总局欺诈风险治理要求03
02 · BENCHMARK

行业现状：三类主流方案的边界

理解现有方案「能做什么、不能做什么」，才能明确本方案补的是什么
方案类型擅长局限
规则引擎 / 决策引擎（Drools、Falcon 等）毫秒级实时决策，确定性好，可解释、可审计以单交易/单账户为视角，缺乏跨账户关联；规则维护成本随欺诈手法演化持续攀升
图风控（Neo4j、TigerGraph、GNN）发现团伙关联、识别资金网络，弥补跨账户盲区强在「发现」，弱在「处置」——识别之后如何自动处置、如何审批、如何核验，仍要另起炉灶
通用 LLM / Agent 方案（LangGraph 等）自然语言推理、证据链生成，理解力强输出不确定、幻觉风险；缺乏风控必需的确定性、人机审批边界与审计追溯

结论

三类方案各有所长，但都缺一条：把「发现」到「处置」再到「核验」串成可审计的闭环，并在其中守住「高风险必由人确认」的边界。这正是本方案要补的位置。

对标参考：Stripe Radar / FIS Falcon / 图风控实践 / LangGraph 多 Agent 风控04
03 · APPROACH

突破方向：确定性打底，LLM 增强，人守住边界

三条设计主线，回应前面每一类方案的短板

五阶段闭环

不是孤立的「检测」，而是 信号聚合 → 根因定位 → 处置执行 → 核验审计 → 知识沉淀 的完整链路。每一次处置都有核验，每一次误判都回流为知识，系统越用越准。

人机边界清晰

低风险可自动处置，高风险一律由人最终确认。Agent 负责建议与执行低风险动作，账户冻结、大额处置必须经过人工审批——让自动化「敢用、可控」。

确定性优先，LLM 增强

核心评分、状态迁移、处置门禁全部由可复现的规则内核执行；LLM 只做语义检索与根因推理增强。即使没有 LLM Key，系统照常闭环运行，LLM 是「加分项」而非「前提」。

低风险（分 < 40，小额）

直接进入自动处置通道，无需人工审批。系统自动完成放行或拦截，并把决策依据写进审计。

中风险（40–69）

一律转人工复核，由风控值班员判断「放行 / 拦截 / 升级」。系统不做自动处置。

高风险（≥ 70）

先深度调查取证，生成处置建议后必须经人工审批。批准才执行；驳回则回退人工复核，且禁止再进入自动通道。

风险阈值可通过配置中心动态调整，无需重启08

08 · SCENARIO 1

场景一 · 低风险自动处置（全自动，零人工）

立案之后无人推动，事件工作器自动把案件推进到「已处置」
